Goal

jev-claw is an agent that lets a fast judge make the small decisions, so the slow model runs only when text is needed. The judge is Jev, the TypeSafe model that returns a typed verdict (yes or no, one choice, or a score) with a number, and never writes text.

Measured today with bun scripts/jev/jev-smoke.ts --calls 5: 239 ms median, 643 ms worst. One call carries many questions, and they run in parallel. A normal model turn takes seconds. That gap is the product.

"Fastest" needs a number before it is a claim. The plan measures three things from the first phase: cold start of the binary, time from user input to first useful action, and the count of slow model turns that a Jev verdict replaced.

The multi-agent model, d9: every agent is a tokio task that owns a mailbox. Messages are typed and serialized, so the log can replay any run. A parent still spawns children as Hermes does, but a child can also message a peer, claim work on the task board, or hand off. The orchestrator is one actor, not special code. Jev sits at the risk gates and the stop or continue points of every actor (d13).

flowchart LR
  O[Orchestrator actor] -- spawn --> A[Worker A]
  O -- spawn --> B[Worker B]
  A -- typed message --> B
  B -- typed message --> A
  A -- claim / done --> T[(Task board)]
  B -- claim / done --> T
  O -- read --> T
  A -. every message .-> L[(Replayable log)]
  B -. every message .-> L
  O -. every message .-> L
  J{Jev gates} --- A
  J --- B

The desktop app is apps/desktop: a Tauri 2 shell whose lib.rs links the core, streams over the Channel API, and hosts the Hermes React dashboard against claw-rpc (d11, your call).

Four rules hold in the product. Jev sorts a case into named buckets and never writes text or calls a tool. Every choice keeps a no-match option. undecided never means yes: it takes the safe default, which for a tool is "ask the user". Every verdict is logged with its masked question, number and latency.

Where the speed comes from: a native binary with no runtime to start, many Jev questions in one call, Jev checks that run at the same time as the model stream, and skill selection by a verdict instead of a model planning turn.

Self-improvement loop

The loop comes from Vesper. jev-claw takes the ideas, not the code.

Vesper partWhat it doesWhat jev-claw takes
auto-evolveA daily task reads run and error counts, asks a model for skill and fix proposals as JSON, and records them. It installs a skill only from an allowlist, only when switched onThe gather, reflect, parse, propose steps as Rust types. Jev scores each proposal before a person sees it
skill-trainRewrites one SKILL.md, tests it on tasks it did not train on, keeps it only if strictly better. A person runs accept. revert restores the old fileThe same accept rule. Jev score verdicts replace the slow model-as-judge scorer
self-improveRuns health checks first and hands code work to a separate pipeline under human reviewThe rule that code changes are proposals only
flowchart LR
  A[Run log: verdicts and outcomes] --> B[Gather digest]
  B --> C[Model proposes skill text change]
  C --> D[Jev scores on held-out tasks]
  D -->|strictly better| E[Candidate file]
  D -->|not better| F[Drop]
  E --> G[Owner accepts or reverts]

Guards that stay: untrusted run data is length-capped and framed as data; a malformed model reply changes nothing; a process argument comes only from an allowlist; propose is automatic and apply is a human command; every accepted change has a checkpoint and a revert.

The new part is the decision log. Every verdict is logged with its question, number and latency. When the outcome is known, the pair (verdict, outcome) is a free training and evaluation set for the question packs: a question whose verdicts are often overruled gets rewritten by the same loop.

Risks and open questions

  • Size. Hermes is 516,000 lines of Python and the port is a multi-release program for one owner plus agents. Phase 2 must prove the core is worth it before phase 7 starts.
  • The five hardest parts: the compaction commit-fence semantics, the 1,863 lines of provider-specific recovery in turn_recovery.py, WAL and FTS5 with CJK parity, the 38-provider quirk matrix, and the gateway session lifecycle across 20 plus channels.
  • Jev voted against the multi-agent design (d9, 0.82). The owner overruled it. Phase 3 must show peers talking is worth the extra design, or the plan falls back to the Jev pick.
  • ElevenLabs is a second vendor and a per-minute bill. The voice trait keeps the exit open.
  • Jev is one vendor and one network hop. If it is down, every gate is undecided and the agent asks the user each time. The agent must stay usable in that mode.
  • Jev was unsure on open questions today. 22 of 22 design scores and 8 of 8 exclusivity checks were under the bar. Phase 2 measures the decided rate per question; a question under a set rate gets rewritten or removed.
  • No official ZeroClaw speed numbers exist. We measure ZeroClaw ourselves in phase 6 before any public claim.
  • Masking moves with the judge. The copied mask has Edel patterns. The Rust port needs a general list plus a per-user list.
  • The copied skill text is Edel-specific. The money path class must become a general "stop and ask a person" class that each user sets.
  • The Rust toolchain is not on this machine. cargo and rustc were not found.
